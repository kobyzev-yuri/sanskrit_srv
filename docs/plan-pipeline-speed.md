# План доработок: ускорение конвейера (extract → LLM)

Статус: **согласовано, не внедрять на текущем VPS (~1 ГБ RAM)**.  
Сейчас: один воркер, последовательно, ~10–35 с/страница (vision LLM).  
Цель после апгрейда памяти: контролируемый параллелизм без потери устойчивости и без «сжигания» квоты ProxyAPI.

Связанные файлы сегодня: `backend/app/worker.py`, `backend/app/services/pipeline.py`, `backend/app/services/llm_draft.py`.

---

## 1. Проблема

| Сейчас | Почему медленно |
|--------|-----------------|
| Один job на всю книгу | рестарт/зависание бьёт по всему прогону |
| Extract + LLM в одном потоке | LLM ждёт сеть, CPU простаивает |
| SQLite + один писатель | при N воркерах — блокировки |
| Нет лимита параллелизма в конфиге | нельзя безопасно «включить газ» после апгрейда RAM |

«Мгновенный» прогон уже готовых страниц (`skip_draft`) — это не ускорение LLM, а пропуск. На новой книге каждая страница = extract PNG + вызов Gemini.

## 2. Целевая архитектура

```
                    ┌─────────────────────┐
  upload/confirm →  │  job: pipeline_book │  (оркестратор)
                    └─────────┬───────────┘
                              │ создаёт page-jobs
              ┌───────────────┼───────────────┐
              ▼               ▼               ▼
        page_job #1     page_job #2     page_job #N
              │               │               │
              ▼               ▼               ▼
     ┌────────────────┐  (очередь)   ┌────────────────┐
     │ extract pool   │─────────────▶│  LLM pool      │
     │ concurrency=1  │   PNG path   │  concurrency=K │
     └────────────────┘              └────────────────┘
              │                               │
              └──────────▶ SQLite/PG ◀────────┘
                         (статусы страниц)
```

Принципы:

1. **Страница = единица работы** (отдельная job или задача в очереди).
2. **Extract и LLM разделены** — разные лимиты параллелизма.
3. **Картинки не копятся в RAM** — pixmap → файл → сразу освободить.
4. **K задаётся конфигом** — на слабом хосте `K=1`, после RAM — `K=4…8`.
5. **Квота 402** останавливает всю очередь LLM, не только один page-job.

## 3. Этапы внедрения

### Этап A — подготовка (можно на текущем железе, низкий риск)

- [ ] Конфиг: `PIPELINE_EXTRACT_CONCURRENCY=1`, `PIPELINE_LLM_CONCURRENCY=1`
- [ ] Job payload / progress: `done`, `total`, `current_pages[]`, `errors[]`
- [ ] Явный skip уже готовых страниц + метрика «skipped / llm / failed»
- [ ] Reclaim stale `running` (уже есть) + таймаут «нет прогресса N минут → requeue page»
- [ ] Логи: длительность extract / LLM / total на страницу (для ETA в UI)

**Критерий готовности:** при `LLM_CONCURRENCY=1` поведение как сейчас, но измеримее.

### Этап B — page-jobs (после стабилизации A)

- [ ] Оркестратор `pipeline_project` только создаёт/перечисляет page-задачи
- [ ] Воркер берёт `pipeline_page` из очереди
- [ ] Идемпотентность: повтор page-job не дублирует версии без `force`
- [ ] UI: прогресс по факту `expert_done` / `failed`, не по одному `current_page`

**Критерий:** рестарт воркера продолжает книгу без «обнуления ощущения прогресса».

### Этап C — параллельный LLM (когда добавят RAM)

- [ ] Пул LLM-воркеров или asyncio-семафор с `PIPELINE_LLM_CONCURRENCY=K`
- [ ] Extract остаётся `concurrency=1` (или 2 max) — узкое место по RAM/PDF
- [ ] Общий rate-limit ProxyAPI (запросов/мин) + backoff 429
- [ ] Жёсткий стоп очереди при `LlmQuotaError` (как сейчас на book-job)
- [ ] Ограничение размера pixmap / DPI в конфиге (`EXTRACT_DPI`)

**Ориентир ускорения:** при K=4 и том же API — до ~3–4× wall-clock (не линейно из‑за лимитов API).

### Этап D — БД и деплой под нагрузку

- [ ] Postgres вместо SQLite (или отдельный writer + очередь)
- [ ] Redis/очередь (RQ/Arq/Celery) — опционально, если процессов >1 хоста
- [ ] MemoryMax systemd под новые лимиты; отдельный unit на extract vs llm — по желанию
- [ ] Алерты: очередь растёт, нет прогресса, 402, swap thrash

## 4. Конфиг (черновик env)

```bash
# сейчас / безопасный дефолт
PIPELINE_EXTRACT_CONCURRENCY=1
PIPELINE_LLM_CONCURRENCY=1
PIPELINE_PAGE_TIMEOUT_SEC=180
EXTRACT_DPI=140

# после апгрейда RAM (пример)
# PIPELINE_LLM_CONCURRENCY=4
# EXTRACT_DPI=160
```

Не поднимать `LLM_CONCURRENCY` на хосте с ~1 ГБ: пик = N×(pixmap + httpx + python) легко уйдёт в swap и станет *медленнее*.

---

## 5. Риски и как гасить

| Риск | Митигация |
|------|-----------|
| OOM / swap | низкий extract concurrency; не держать PDF+N PNG в памяти; MemoryMax |
| SQLite lock | один DB-writer или Postgres на этапе C/D |
| 402 / квота | глоба очереди; баннер в UI (уже задел) |
| Гонки версий страницы | уникальный «активный» page-job; `SELECT FOR UPDATE` / статус `llm_draft` |
| Качество при спешке | параллелизм не меняет промпт; `force_llm` только явно |

---

## 6. Что не делаем в этом плане

- Смена модели «лишь бы быстрее» без замера качества деванагари
- Массовый OCR вместо vision без отдельного решения по типу PDF
- Docker/K8s до появления реальной многомашинности

---

## 7. Порядок работ (кратко)

1. A — конфиг + метрики + таймауты страницы  
2. B — page-jobs + устойчивый resume  
3. Апгрейд RAM на VPS  
4. C — `LLM_CONCURRENCY=K` + rate-limit  
5. D — Postgres/очередь по необходимости  

Пока этап C **не включать**. Текущий последовательный режим — осознанный trade-off стабильности на маленькой машине.
